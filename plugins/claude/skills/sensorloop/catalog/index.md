# The catalog

Every sensor, tool and loop, one line each, with what it is linked to. The card behind a line is
`sensors/<id>.md`, `tools/<id>.md` or `loops/<id>.md` beside this file. Generated from the catalog; do not edit.

## Sensors (35)

- `agent-activity`: **Agent activity** (computational). Watches the agent's own tool calls and sessions, and reports the patterns that mean the agent is in trouble. Tools: `agent-hooks`, `session-transcripts`. Loops: `stall-detector`.
- `api-compatibility`: **API compatibility check** (computational). Compares the public interface after a change with a baseline, such as the last release, and reports each difference that breaks a caller. Tools: `api-diff`, `schema-driven-api-tester`. Loops: `api-breaking-changes`.
- `browser-run`: **Browser run** (computational). Drives a scripted flow through a page in a real browser, and reports the step that broke. Tools: `accessibility-engine`, `agent-browser-access`, `browser-automation`, `component-workshop`, `page-audit`, `preview-environment`, `test-fixtures`. Loops: `lighthouse-ci`, `e2e-browser`.
- `build-and-types`: **Build and type check** (computational). Compiles the code or checks its types, and reports each error with its place. Tools: `project-build-command`, `language-server`, `type-checker`. Loops: `agent-branch-integration`, `type-check-and-build`.
- `ci-results`: **CI results** (computational). Reads the results of the project's CI for a commit: which jobs passed, which failed, and the failing step's log. Tools: `ci-system`, `code-host`. Loops: `preview-environments`, `ci-clean-infra`.
- `coverage-mutants`: **Coverage and mutation** (computational). Shows what the tests do not check: lines no test runs, and changes to the code that no test notices. Tools: `coverage-tool`, `mutation-tester`. Loops: `mutation-testing`.
- `flow-metrics`: **Delivery flow metrics** (computational). Measures how work flows through the project over weeks: how long changes wait, how soon they get a first review, how old the backlog is, how much CI costs. Tools: `code-host`. Loops: `repo-health-agent`.
- `dependency-graph`: **Dependency graph** (computational). Measures the graph of imports between modules (cycles, fan-in, fan-out) and compares it with an approved baseline. Tools: `dependency-graph-analyser`. Loops: `architecture-fitness-functions`.
- `error-tracker`: **Error tracker** (computational). Reads the errors real users hit, grouped into issues with stack traces and counts, and whether they came back after a fix. Tools: `error-tracking-service`. Loops: `release-confirmation`, `error-tracking`.
- `eval-set`: **Eval set** (computational). Runs an agent, a prompt or a skill many times on cases with known answers, and reports how often it gets them right. Tools: `eval-runner`, `model-api`. Loops: `agent-calibration`, `skill-trigger-eval`, `llm-evals`.
- `human-answer`: **Human answer** (human). The agent asks a person a structured question (approve a plan, choose an option, confirm a risky action) and gets an answer it can act on. Tools: `code-host`, `permission-rules`, `plan-mode`, `question-tool`. Loops: `spec-before-tests`, `approval-reviewer-agent`, `plan-approval`, `risky-action-gates`, `user-feedback`, `triage`, `text-from-a-brief`.
- `human-review`: **Human review** (human). A person looks at the result (the diff, a demo, a sample of the agent's work, the product itself) and says whether it is what was wanted. Tools: `code-host`, `component-workshop`, `issue-tracker`. Loops: `correction-becomes-rule`, `human-diff-review`, `agent-calibration`, `approved-fixtures`, `result-demo`.
- `input-fault-injection`: **Input and fault injection** (computational). Runs the code on generated inputs or with broken dependencies, and reports the smallest case that makes it fail. Tools: `chaos-platform`, `fault-proxy`, `fuzzer`, `property-testing-library`, `schema-driven-api-tester`. Loops: `fault-injection`.
- `isolation-probe`: **Isolation probe** (computational). Checks from inside an agent's environment that it is isolated: no network it should not reach, no secrets it should not see, nothing left after teardown. Tools: `isolated-environment`. Loops: `isolated-environment`.
- `linter`: **Linter** (computational). Checks code or prose against rules, and names each violation with its place and the rule it breaks. Tools: `dependency-graph-analyser`, `project-linter`, `migration-linter`, `prose-linter`, `syntax-tree-rules`, `translation-catalog-check`. Loops: `architecture-fitness-functions`, `db-migration-lint`, `lint-with-fix-instructions`, `text-from-a-brief`.
- `live-supervision`: **Live supervision** (human). A person follows the agent's work as it happens, and interrupts when it drifts. Tools: `interrupt-and-rewind`. Loops: `observe-and-interrupt`.
- `llm-judge`: **LLM judge** (inferential). A model scores a result, a screenshot, a sample of logs or the risk of an action against a rubric. Tools: `fresh-context-agent`, `model-api`, `permission-rules`. Loops: `approval-reviewer-agent`, `llm-evals`, `triage`.
- `llm-reviewer`: **LLM reviewer** (inferential). A separate agent with a fresh context reads a diff, a document or some code against a checklist or a policy, and lists what it finds. Tools: `fresh-context-agent`. Loops: `verification-subagent`, `agent-code-review`, `third-party-extension-scan`, `repo-health-agent`, `text-from-a-brief`.
- `logs`: **Logs** (computational). Queries the logs of a run or a release, and reports the errors in them, grouped and counted. Tools: `log-store`. Loops: `preview-environments`, `release-confirmation`, `structured-logs`, `health-checks-smoke`.
- `loop-outcomes`: **Loop outcomes** (computational). Reads the record of what the loops caught and missed (escapes, corrections, unconfirmed releases) to find the loop that should have caught a problem earlier. Tools: `outcome-log`, `session-transcripts`. Loops: `correction-becomes-rule`.

- `metrics`: **Metrics and SLOs** (computational). Queries the service's metrics (error rates, latency, resource use) and compares them with a limit, a service level objective (SLO) or the previous version. Tools: `metrics-store`, `rollout-controller`. Loops: `release-confirmation`.
- `model-check`: **Model check** (computational). A model checker explores, within set bounds, every reachable state of a small formal model of one critical part, such as shared credits or a protocol between services, and reports either a trace that breaks a property or no violation. Tools: `model-checker`. Loops: none yet.
- `performance-measure`: **Performance measurement** (computational). Measures time, memory, size or load against a baseline or a limit, and reports what got worse. Tools: `benchmark-harness`, `load-generator`, `page-audit`, `preview-environment`, `profiler`, `size-budget`, `trace-store`. Loops: `lighthouse-ci`, `load-testing`.
- `repository-state`: **Repository state** (computational). Reads the repository's state and diff directly, instead of taking the agent's word for what changed. Tools: `git`. Loops: `afk-run-handoff`, `agent-branch-integration`.
- `requirement-trace`: **Requirement trace** (computational). Follows the links from each requirement to the spec elements that cover it and the tests that check it, and back, and reports every requirement, element or test left without one. Tools: `executable-spec`. Loops: `spec-before-tests`.
- `screenshot`: **Screenshot and recording** (computational). Captures what the interface looks like, as an image or a video, for a comparison or as evidence. Tools: `agent-browser-access`, `browser-automation`, `component-workshop`, `scripted-terminal`. Loops: `result-demo`.
- `security-scanner`: **Security scanner** (computational). Scans code, history, dependencies or a running app for known security problems and licence breaches. Tools: `workflow-checker`, `dependency-scanner`, `dynamic-security-scanner`, `preview-environment`, `secret-scanner`, `static-security-scanner`, `syntax-tree-rules`. Loops: `agent-ci-hardening`, `dependency-scanning-sbom`, `secret-scanning`, `dast`.
- `smoke-probe`: **Smoke and health probe** (computational). Starts the built artifact or reaches the deployed release, and checks that it answers and that its main paths work. Tools: `artifact-verification`, `backup-restore`, `health-endpoints`, `http-client`, `preview-environment`, `rollout-controller`. Loops: `preview-environments`, `shipped-artifact-check`, `backup-restore-rollback`, `health-checks-smoke`, `config-validation`.
- `spec-completeness`: **Spec completeness** (computational). Checks the spec for gaps a test writer would have to guess at, before any test or code is written from it. Tools: `executable-spec`. Loops: `spec-before-tests`.
- `structure-check`: **Structure check** (computational). Checks a file that has a required shape, such as a config, a CI workflow, a changelog or a release artifact, against that shape or a policy. Tools: `artifact-verification`, `workflow-checker`, `link-checker`, `schema-validator`, `translation-catalog-check`. Loops: `agent-ci-hardening`, `shipped-artifact-check`, `config-validation`.
- `terminal-run`: **Terminal run** (computational). Drives a terminal app through a scripted session at a fixed size, sending keys and reading the rendered screen. Tools: `scripted-terminal`. Loops: none yet.
- `test-runner`: **Test runner** (computational). Runs the project's tests on the changed code and reports which pass and which fail. Tools: `contract-broker`, `scripted-model`, `snapshot-library`, `project-test-command`, `test-fixtures`, `throwaway-dependencies`. Loops: `bug-failing-test-fix`, `db-migration-lint`, `verification-subagent`, `approved-fixtures`, `agent-branch-integration`, `red-green-tdd`, `run-tests-first`, `scripted-model-tests`.
- `traces`: **Traces** (computational). Queries the traces of requests through the system, and reports the spans that failed or took too long. Tools: `trace-store`. Loops: `load-testing`, `traces-opentelemetry`.

## Loops (52)

- `bug-failing-test-fix`: **A bug starts with a failing test**. The agent turns a bug into a test that fails for the bug's reason, changes the code until it passes, and runs the whole suite. Reads: `test-runner`. When: On every bug fix, before the code is changed and again after.
- `isolated-environment`: **A clean environment for each task**. Each task gets a new environment of its own, which checks its own isolation before the agent starts and is thrown away at the end, so the sensors give the same result for the same code. Reads: `isolation-probe`. When: At the start of each task, before the agent starts; while it works, on every sandbox process; after teardown; and in CI, on every change to the setup files.
- `spec-before-tests`: **A complete spec before the tests**. Tests are derived only from a spec with nothing left to guess. Each requirement is traced to the spec elements and tests that cover it, and each functional one names the production signal that confirms it after the release. Reads: `requirement-trace`, `spec-completeness`, `human-answer`. When: After every edit to the requirements or the spec, before tests are derived from it; again once the tests are written, and in CI on every pull request that touches the spec or the tests.
- `correction-becomes-rule`: **A correction becomes a rule**. Every correction a person makes is logged at the phase that should have caught it, and the second of the same kind becomes a check, a reviewer's rule or a line in the agent's instructions. Reads: `human-review`, `loop-outcomes`. When: Each time a person corrects the agent: in the session, in a review comment or by reverting a change. Weekly, the session transcripts are searched for missed corrections, including an error that took the agent more than three attempts, and the outcome log is read for kinds that came back.
- `human-diff-review`: **A person reviews the diff**. A person reads the pull request's diff and comments on it. The agent answers each unresolved comment in its thread, with a change, a reply or a refusal and its reason, and the merge waits for the person's approval. Reads: `human-review`. When: On each pull request once its automated checks pass and each high finding of the reviewer agents is fixed or ruled on; then after each round of comments, when the agent works on the threads still unresolved.
- `preview-environments`: **A preview environment for each change**. Every pull request is deployed to an environment of its own, at its own address, so that the checks needing a running app can test that change alone, before it is merged. Reads: `smoke-probe`, `logs`, `ci-results`. When: On every push to a pull request from the repository's own branches, once its deploy job has finished; and on a schedule, for environments of pull requests already closed. A fork's pull request gets no preview, so its checks that need a running app wait until after the merge.
- `approval-reviewer-agent`: **A reviewer answers permission prompts**. In a run nobody watches, a read-only reviewer model answers the agent's permission prompts in place of a person. It scores the action's risk and whether the person authorised it, and a denial forbids reaching the same effect another way. Reads: `llm-judge`, `human-answer`. When: Each time the agent asks for an action that no allow or deny rule settles and its sandbox does not cover, at the point where a permission prompt would be shown.
- `agent-ci-hardening`: **Agents in CI keep their guards**. A CI check finds every workflow job that runs a coding agent, and fails when one lacks a guard: a filtered network, a permission mode that reviews calls, a tool list and a turn cap, or a job with no write token where the agent reads text anyone can write. Reads: `structure-check`, `security-scanner`. When: On every pull request and every push to the main branch, over all the workflows and the actions they call.
- `afk-run-handoff`: **An unattended run ends in a hand-off or a reason**. After an agent runs with nobody watching, a wrapper reads git, not the agent's report, and either hands the work on or blocks the item with the reason and the one step that retries it. No item stays in progress after its run. Reads: `repository-state`. When: Before an unattended run starts, on the item it was given; and after the agent's process exits, whether it finished, crashed or ran out of time.
- `plan-approval`: **Approve the plan first**. Before it changes anything, the agent studies the code read-only and writes a plan that opens with the task in its own words (what it understood, what it will not do, and what will show it is done). A person corrects or approves it, and the agent then works by the plan on its own. Reads: `human-answer`. When: Before the agent's first edit on a task whose direction is not yet settled, once it has read the code; again whenever the work needs a requirement or a change of approach the approved plan does not name.
- `architecture-fitness-functions`: **Architecture rules**. Rules for the direction of imports between layers fail as soon as the agent adds an import that breaks them, and each message describes the layers, so the agent moves the code where it belongs. Reads: `linter`, `dependency-graph`. When: After the agent adds or moves an import, at each commit, and in CI as the final run.
- `risky-action-gates`: **Ask before the irreversible**. Before an action that cannot be undone, the agent stops, and a person confirms or refuses it. Reads: `human-answer`. When: Before an action that cannot be undone, such as a deploy, a migration, deleting data, a push to a protected branch, or a message sent outside the project. In CI, a check confirms that the gates are still in place.
- `lighthouse-ci`: **Audit the preview's pages**. A page audit loads the preview's main pages in a browser several times and scores them, and fails when a score falls below the project's threshold, such as performance under 0.9. The agent reads the report to find the audits that cost the points, and fixes them. Reads: `performance-measure`, `browser-run`. When: In a CI job after each deploy of a pull request's preview, once the preview is ready. While it works, the agent may audit one page against its own preview.
- `agent-calibration`: **Calibrate before it blocks**. An expert grades a sample of results pass or fail, each with a critique, and the grades become the cases a judge or reviewer agent is scored against. The agent may block only once it agrees with them at a rate a person approved. Reads: `human-review`, `eval-set`. When: When a loop's judge, reviewer or refuter is written; again whenever its prompt, its model or the agent that writes its prompt changes, before it blocks again; and on a schedule, when the expert grades a fresh sample of its verdicts in real use.
- `db-migration-lint`: **Check each migration before it runs**. A migration linter names a dangerous operation in a new database migration, such as a table lock or a destructive change, and the agent rewrites the migration; then it is applied, rolled back and applied again on a throwaway database. A bad migration does its damage when it runs, and reverting the code does not undo it. Reads: `linter`, `test-runner`. When: On every change that adds a migration or edits one that has not run anywhere yet, in the agent's session before it commits, and again in CI on the pull request.
- `verification-subagent`: **Check the claim of done**. When the working agent says a task is done, a separate agent with a fresh context gets the claim and the requirement, not the reasoning, and tries to prove the claim wrong by running the tests and the app. Reads: `llm-reviewer`, `test-runner`, `manual-probe`. When: Each time the working agent says a task is done, before its turn ends or it opens a pull request; again after each fix, with a new refuter; and in CI on the pull request.
- `shipped-artifact-check`: **Check what ships before the channel moves**. The release installs the exact package, binary or image it will publish into an empty place and runs it, publishes it without moving the channel pointer, verifies it from the registry, and only then moves the pointer (`latest`, `stable`, an install script). Moving the pointer back does not repair the installs that already failed. Reads: `structure-check`, `smoke-probe`. When: On every release, as required steps of the release job between the build and the pointer; and on every pull request, a quick pack, install and run of the package.
- `approved-fixtures`: **Compare with approved output**. A test compares the output with a reference stored in the repository. The agent fixes a difference the change does not explain, and proposes one it does explain to a person, who alone approves the new reference. Reads: `test-runner`, `human-review`. When: On every run of the tests, locally and in CI on every pull request; and in CI on every pull request that changes a reference file.
- `release-confirmation`: **Confirm the release in production**. After a release reaches production, a job judges a window of real traffic, and the change is confirmed only if production runs it, its own signal appeared often enough, and nothing is worse than under the previous version. Reads: `logs`, `metrics`, `error-tracker`. When: After each deploy to production, once a window of real traffic has passed (at least a set time and a set number of events on the changed path, up to a cap).
- `skill-trigger-eval`: **Does the skill load when it should**. Realistic requests that should and should not use a skill, a subagent or a command run several times each, and the eval counts how often the agent loads it. A rewritten description is kept only if it does better on requests it was not tuned on. Reads: `eval-set`. When: On every change to the description of a skill, a subagent or a command, to the coding agent or to the model it runs on; and on demand, when a person asks to tune a description.
- `llm-evals`: **Evals on every prompt change**. After each change to a prompt, a tool description or the model, the agent runs the feature on a suite of cases several times, and a drop in the pass rate fails the change. Reads: `eval-set`, `llm-judge`. When: After each change to a prompt, a tool description, the model or a parameter the feature uses, before the agent says it is done; in CI, on every pull request that touches one of them; and every night on the main branch, to learn which cases are stable.
- `user-feedback`: **Feedback becomes tested criteria**. One item of user feedback becomes acceptance criteria, each tied to a scenario that reproduces what the user met, and a person approves them before any work. The agent works until the tests made from them pass. Reads: `user-feedback`, `human-answer`. When: When an item of feedback that asks the product to do something new or different is picked up for work, before any code is written; again when the agent says the work is done, and in CI on its pull request. After the release, the item's topic is read again in the feedback.
- `error-tracking`: **Fix the errors users hit**. The agent takes an issue from the top of the error tracker, reproduces it with a failing test, then fixes the code, and the fix counts only once the issue stops under the release that carries it. Reads: `error-tracker`. When: Every day, when a scheduled job collects the top new issues, the escalating ones and the ones that came back after a fix; and after the release that carries a fix, once a window of real traffic has passed (at least a set time and a set number of runs of the issue's path, up to a cap).
- `ci-clean-infra`: **Fix what fails in CI**. The agent pushes, CI runs the checks on clean machines, and the agent fixes what fails; after the second red round, a person takes over. Reads: `ci-results`. When: After each push, once CI has finished the run for the branch's latest commit.
- `agent-code-review`: **Fresh-context code review**. Reviewer agents with a fresh context read the committed diff, and the coding agent fixes the high findings a second pass confirms. Each re-review checks only the findings not yet addressed, for at most five rounds. Reads: `llm-reviewer`. When: After the coding agent's tests pass and its work is committed, before it opens a pull request; then once per round of fixes, on the fix diff; and again in CI on the pull request.
- `api-breaking-changes`: **Keep the API compatible**. When the agent changes an API description, a library's public API or data that released clients read, a check compares the change with what callers already have, and the agent restores compatibility. Reads: `api-compatibility`. When: Before each commit that changes an API description, a library's public API or data that released clients read; and again in CI as the final run.
- `lint-with-fix-instructions`: **Lint with fix instructions**. Every lint violation reaches the agent with a text that says how to fix it, so the agent fixes the cause instead of silencing the rule. Reads: `linter`. When: At each commit, and again in CI as the final run.
- `load-testing`: **Load test a preview**. The agent runs a load scenario against the preview environment of its change, and when the response time or the rate of failed requests goes over its threshold, it finds the bottleneck in the traces and fixes it. Reads: `performance-measure`, `traces`. When: In a CI job after each deploy of a pull request's preview environment, or on a schedule against staging; the agent may also run a scenario against its own preview while it works. The traces are read when a threshold fails.
- `agent-branch-integration`: **Merge parallel agents' branches one at a time**. Agents that work in parallel each leave a branch. A wrapper asks git which branches are ready, merges them into the target one at a time with the type check and the tests after each, and fails a merge that moved nothing or left conflicts. Reads: `repository-state`, `build-and-types`, `test-runner`. When: After each cycle of parallel runs and before the next is planned, once for every branch git shows ahead of the target; and when the base moves under an open pull request.
- `dependency-scanning-sbom`: **No known-vulnerable dependencies**. A scanner checks the project's dependencies against vulnerability databases and the licences the project allows, and the agent moves each vulnerable package to a safe version, or replaces a package under a licence the project does not allow, before the change is merged. Reads: `security-scanner`. When: On every pull request that changes a manifest or a lockfile, and every night over the SBOMs of the releases in production.
- `secret-scanning`: **No secrets in commits**. A secret scanner checks every commit before it is made and again in CI, and the agent moves each key it finds out of the code. A secret that has already been pushed goes to a person, who revokes it. Reads: `security-scanner`. When: Before each commit, on the staged changes; in CI, on the commits of every pull request; and on a schedule, over the whole history.
- `structured-logs`: **Read the logs**. After running a scenario, the agent queries the structured logs of its own run for errors and fixes the cause, until the query finds none or the agent hands the error to a person. Reads: `logs`. When: After the agent runs a scenario through the app in its worktree, before it says the work is done; and in CI, after the end-to-end job, against CI's own log store.
- `traces-opentelemetry`: **Read the traces**. After running a scenario, the agent queries the traces of its own run for spans that failed or went over budget, and fixes the cause until the same queries return nothing. Reads: `traces`. When: After the agent runs a scenario through the services it changed, before it says the work is done; and in CI, against CI's own collector and trace store.
- `third-party-extension-scan`: **Read third-party extensions before they run**. Before a third-party plugin, skill or MCP server is added or moved to a new commit, a reviewer reads every file it ships against a written policy, and a fail keeps it out. Reads: `llm-reviewer`. When: On every pull request that adds an extension or moves its pin, once per new pin; and on every pull request that changes the policy, over every pinned extension.
- `red-green-tdd`: **Red, then green**. A change in behaviour starts with a test that fails for the right reason, and ends when that test and the rest of the suite pass. Reads: `test-runner`. When: Before the code for a new behaviour or a fix is written, and again after it.
- `repo-health-agent`: **Repository health**. Every day a job records the project's delivery metrics, an agent turns the worst trend into one proposed change, and a critic must approve it before it becomes a draft pull request a person reviews. Reads: `flow-metrics`, `llm-reviewer`. When: Every day, from a scheduled CI job that first records the day's metrics, and when a collaborator, member or owner mentions the agent on an issue; the critic reads each proposed change before anything is published; and four weeks after a change merges, its metric is read again.
- `backup-restore-rollback`: **Restore and rollback drills**. On a schedule, a job restores the database from a real backup into a throwaway place and checks the data, and rolls a release back on staging; when a check fails, the agent fixes the procedure. A backup never restored may not restore on the day it is needed, and then the data is lost. Reads: `smoke-probe`. When: The restore weekly, and after every change to the backup job or its configuration; the rollback nightly on staging, against the latest release candidate.
- `run-tests-first`: **Run the tests first**. Before changing anything, the agent runs the whole suite and keeps the result, so it never takes an old failure for its own regression. Reads: `test-runner`. When: At the start of a task, before any change; and at its end, compared test by test with that first run.
- `dast`: **Security scan of the running preview**. A dynamic security scanner probes the deployed preview from outside, the way an attacker would, with a passive scan on every deploy and an active scan with attacks before a release. The agent fixes each alert that the project's rules file marks as a failure. Reads: `security-scanner`. When: After each deploy of a pull request's preview, once it is ready, a passive scan; nightly and before each release, an active scan against the preview or staging.
- `result-demo`: **Show the result**. Once the automated checks pass, the agent shows a person the working feature, with screenshots, a recording or the real output of a command, and the person judges the behaviour, not the code. Reads: `human-review`, `screenshot`. When: As the task's last step before the merge, once its automated checks pass; the evidence is checked in CI on the pull request.
- `health-checks-smoke`: **Smoke test after a deploy**. After each deploy to a preview environment or to staging, a job checks that the new version is ready and runs a few smoke checks against it, and a red result stops the release there. Reads: `smoke-probe`, `logs`. When: Right after each deploy to a preview environment or to staging, before the release is promoted to the next stage.
- `stall-detector`: **Stall detector**. A hook tells the agent to step back when it repeats the same call, or the same cycle of calls, five times, and a second stall stops it for a person. - `scripted-model-tests`: **Tests against a scripted model**. Code around a model, such as the agent loop, tool dispatch, retries and compaction, is tested against a fake provider that replays scripted replies and tool calls. - `mutation-testing`: **Tests that notice a change**. The agent checks its tests from outside. Coverage of the changed lines shows code no test runs, mutation testing on the changed files shows changes to the code no test notices, and each gap gets a test that fails on it. Reads: `coverage-mutants`. When: Before the agent says a change is done, once its tests pass; in CI on every pull request; and on a schedule over the whole code, and for each written concern, such as data leaks, over the code it covers.
- `triage`: **Triage what comes in**. Each incoming item, from an alert to a user's message, joins an open item on the same problem or is sorted as a fix, a new feature, maintenance or a question for a person. - `agentic-manual-testing`: **Try it by hand**. The agent runs what it just wrote the way a user of that code would, and turns each defect it finds into a test that fails before the fix and passes after it. Reads: `manual-probe`. - `type-check-and-build`: **Type check and build**. After an edit, the agent runs the type checker and the build, and fixes each new error at its file and line until neither reports one. Reads: `build-and-types`. When: After each edit (the type checker, or the language server's diagnostics), and before the turn ends (the build).
- `config-validation`: **Validate the configuration**. Reads: `structure-check`, `smoke-probe`. - `observe-and-interrupt`: **Watch and step in**. The person does not approve each step.
